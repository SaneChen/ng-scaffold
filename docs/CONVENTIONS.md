# Engineering conventions

These rules apply to every commit on the `ng-matero` branch. They complement the Angular
best practices in [`CLAUDE.md`](../CLAUDE.md) (generated by Angular CLI 22) and the plan in
[`ROADMAP.md`](./ROADMAP.md).

## 1. Toolchain

| Tool        | Version                            | Notes                                         |
| ----------- | ---------------------------------- | --------------------------------------------- |
| Node.js     | `^22.22.3 \|\| ^24.15.0 \|\| >=26` | Required by Angular CLI 22.2                  |
| Yarn        | `1.22.x` (classic)                 | The only package manager of this repository   |
| Angular CLI | `22.2.x`                           | Always run through the workspace: `yarn ng …` |

## 2. Respect the `ng new` baseline

The first commit of this repository is the untouched output of `ng new ng-scaffold`. Every later
commit must keep its traces whenever possible. In order of preference:

1. **Add** — new files, new lines, new array items, new object keys.
2. **Modify** — only when adding is impossible (for example, an option must change).
3. **Delete** — only the documented exceptions in `ROADMAP.md` §1.1.

Practical rules:

- Need another symbol from a module that is already imported? Add a **new** import line
  (`import { inject } from '@angular/core';`) instead of editing the generated one.
- Extending an array or object literal: insert the new entries; keep the original entries and
  comments in place.
- Never rewrite a generated config file wholesale (`.prettierrc`, `.vscode/*`, `angular.json`,
  `tsconfig*.json`). Use `ng config`, `jsonc`-aware edits, or targeted line insertions.
- Formatting changes performed automatically by Angular CLI (it runs `prettier --write` on every
  file a schematic touches) are accepted.

## 3. Generate first, then edit

Create files with the official generators and edit the result — never hand-write a file the CLI
can generate:

| Artifact                  | Command                                                               |
| ------------------------- | --------------------------------------------------------------------- |
| Component                 | `yarn ng g component theme/header`                                    |
| Service                   | `yarn ng g service core/settings/settings-store` (emits `@Service()`) |
| Directive / pipe          | `yarn ng g directive …` / `yarn ng g pipe …`                          |
| Guard (functional)        | `yarn ng g guard core/auth/auth --implements CanActivate`             |
| Interceptor (functional)  | `yarn ng g interceptor core/interceptors/token`                       |
| Interface / enum / class  | `yarn ng g interface …` / `yarn ng g enum …` / `yarn ng g class …`    |
| Environments              | `yarn ng g environments`                                              |
| Libraries with schematics | `yarn ng add @angular/material`, `yarn ng add angular-eslint`         |

File names follow the Angular CLI 22 defaults (no `.component`/`.service` suffix). Pick
descriptive class names instead: `SettingsStore`, `TokenStore`, `LoginApi`, `Preloader`.

## 4. File header comments

Every file created during this branch starts with a header that a newcomer can follow:

```ts
/**
 * <One-sentence purpose of the file.>
 *
 * How this file was built:
 *   1. `yarn ng g service core/settings/settings-store` generated an empty `@Service()` class
 *      and its spec.
 *   2. Added the `options` signal that holds the persisted layout preferences.
 *   3. Added an `effect()` that mirrors `dir`, `lang` and the theme class onto `<html>`.
 *
 * Why: <the design reason, e.g. "templates read signals so default OnPush updates the view">.
 */
```

- Templates (`.html`) and stylesheets (`.scss`) use the equivalent `<!-- … -->` / `// …`
  header only when they contain non-obvious structure; otherwise the component's header covers
  them.
- Lines **added to files generated by `ng new`** carry a short marker comment explaining the
  step, e.g. `// [ng-scaffold] Step 2: register HTTP interceptors.`
- Comments explain _why_; code explains _what_. Avoid restating the code.

## 5. Angular rules (in addition to `CLAUDE.md`)

- **State the template reads is always a signal** (`signal`, `computed`, `linkedSignal`,
  `toSignal`, `input`, `model`). OnPush is the default in v22, so a plain field mutated in a
  callback will not refresh the view.
- Observables are converted at the boundary with `toSignal`, `rxResource` or `httpResource`;
  remaining subscriptions use `takeUntilDestroyed`.
- Side effects that touch the DOM run in `afterNextRender`/`afterEveryRender` or `effect`, not in
  lifecycle hooks; browser globals come from `inject(DOCUMENT)`.
- Every routed page is lazy loaded (`loadComponent` / `loadChildren`).
- New forms use Signal Forms (`@angular/forms/signals`).
- Static images use `NgOptimizedImage`.
- No `CommonModule`, `NgModule`, `ngClass`, `ngStyle`, `@HostBinding`, `@HostListener`,
  `standalone: true`, explicit `ChangeDetectionStrategy.OnPush`, `any`.

## 6. Angular Material (M3)

- Theme with `mat.theme()`; style with system tokens (`var(--mat-sys-*)`) and the official
  `mat.<component>-overrides()` mixins.
- Never target internal `.mat-mdc-*` / `.mdc-*` classes, private Sass members (`mat.$private-*`)
  or M2-only inputs (`color="primary"`).
- Icons use Material Symbols (set up by `ng add @angular/material`).

## 7. Accessibility (WCAG 2.2 AA)

- Icon-only buttons have an `aria-label` (translated).
- Navigation uses `<a routerLink>` or `<button>`; never `href="#"` or clickable `<div>`.
- Keep a visible focus indicator; never `outline: none` without a replacement.
- Expandable menus expose `aria-expanded`; the active link exposes `aria-current`.
- Form fields set `autocomplete` where applicable.

## 8. Commits

- Conventional Commits (`feat(core): …`, `chore(lint): …`), enforced by commitlint.
- The body lists the steps in order: commands that were run, files they produced, the edits made
  on top, and the verification performed (`yarn lint`, `yarn test --watch=false`, `yarn build`).
